# Порівняння асемблера до та після оптимізації

Наведені інструкції взято зі збережених Linux-збірок GCC 13 для одного й того самого [kernels.cpp](../src/kernels.cpp). Усі три варіанти мають `-mavx2`, але відрізняються рівнем оптимізації та дозволом векторизації. Це аналіз фактично отриманого коду, а не прогноз вигляду асемблера в іншому компіляторі.

Повні файли доступні в [results/assembly](../results/assembly/): `kernels_o0.s`, `kernels_scalar.s`, `kernels_o3.s`, дизасемблер виконуваних файлів, журнал компіляції та `vectorization_o3.txt`. У коротких фрагментах нижче прибрано коментарі GCC і службові директиви; знак `; ...` позначає пропущені інструкції. Порядок операндів — Intel: спочатку призначення, потім джерела.

## Як відтворити

```sh
make ARCH_FLAGS=-mavx2 all assembly
objdump -d -Mintel build/image_o0 > build/image_o0.disassembly.txt
objdump -d -Mintel build/image_scalar > build/image_scalar.disassembly.txt
objdump -d -Mintel build/image_o3 > build/image_o3.disassembly.txt
```

У `Makefile` асемблер стадій генерується тими самими ключами оптимізації, що й виконувані файли. Параметри `-S -masm=intel -fverbose-asm` змінюють форму виводу, а звіт `-fopt-info-vec-all` показує рішення векторизатора. Збережені хеші вихідних файлів — у [source_hashes.json](../results/assembly/source_hashes.json).

## 1. Переведення RGB у grayscale

Вихідна формула: `(77*R + 150*G + 29*B + 128) >> 8`.

### Без оптимізації: `O0`

```asm
mov rax, QWORD PTR -8[rbp]
lea rdx, 0[0+rax*4]
mov rax, QWORD PTR -24[rbp]
add rax, rdx
mov eax, DWORD PTR [rax]
imul edx, eax, 77
; ...
imul eax, eax, 150
; ...
imul eax, eax, 29
```

Цикл працює з одним пікселем. Значення індексу й адреси багаторазово завантажуються зі стеку, після чого виконуються окремі скалярні множення. Наприкінці є скалярний `shr edx, 8` та запис одного 32-бітного результату.

### Оптимізована скалярна версія: `O3-scalar`

```asm
imul esi, DWORD PTR [rdi+rax*4], 77
imul edx, DWORD PTR [r9+rax*4], 150
lea edx, 128[rsi+rdx]
imul esi, DWORD PTR [r10+rax*4], 29
add edx, esi
shr edx, 8
mov DWORD PTR [rcx+rax*4], edx
add rax, 1
cmp r8, rax
jne .L8
```

Індекс і базові адреси вже утримуються в регістрах. Зникає значна частина обчислення адрес і роботи зі стеком. Проте кожна ітерація досі формує один результат: `rax` збільшується на один елемент.

### Векторна версія: `O3`

Підготовка завантажує сталі в SIMD-регістри. Фрагмент основного циклу:

```asm
vmovdqu ymm5, YMMWORD PTR [rdi+rax]
vpmulld ymm0, ymm4, YMMWORD PTR [r9+rax]
vpslld ymm2, ymm5, 2
vpaddd ymm2, ymm2, ymm5
vpslld ymm1, ymm2, 4
vpsubd ymm1, ymm1, ymm2
; ...
vpaddd ymm0, ymm0, ymm2
vpaddd ymm0, ymm0, ymm3
vpaddd ymm0, ymm1, ymm0
vpsrld ymm0, ymm0, 8
vmovdqu YMMWORD PTR [rdx+rax], ymm0
add rax, 32
cmp rcx, rax
jne .L9
```

`ymm4` містить вісім копій 77, а `ymm3` — вісім копій 128. `vpmulld` обчислює молодші 32 біти восьми добутків. Для наших невід’ємних малих значень переповнення немає. Множення на деякі інші сталі компілятор замінив зсувами й додаваннями: наприклад, для зеленого каналу `5*G`, потім `75*G`, потім `150*G`. `vpsrld ... ,8` виконує ділення на 256 окремо для кожного елемента. За одну ітерацію записується 32 байти — вісім `uint32_t`.

## 2. Підвищення контрасту та clamp

Формула: `min(255, max(0, ((3*gray + 1) >> 1) - 64))`.

### `O0`

```asm
call _ZSt3maxIiERKT_S2_S2_
mov rdx, rax
mov DWORD PTR -20[rbp], 255
lea rax, -20[rbp]
mov rsi, rdx
mov rdi, rax
call _ZSt3minIiERKT_S2_S2_
```

У цій збірці `std::max<int>` і `std::min<int>` залишилися окремими викликами. Їхні імена після деманглінгу можуть бути видимі в `perf report` та FlameGraph. Тому зникнення цих функцій із профілю після оптимізації пояснюється вбудовуванням їхньої логіки.

### `O3-scalar`

```asm
mov eax, DWORD PTR [rdi+rcx*4]
lea eax, 1[rax+rax*2]
shr eax
sub eax, 64
test eax, eax
jg .L24
xor eax, eax
; ...
.L24:
cmp eax, 254
jle .L16
mov DWORD PTR [rsi+rcx*4], 255
```

Множення на 3 і додавання 1 об’єднано в `lea`. Викликів `std::min/max` немає. Значення обмежується скалярними перевірками й переходами. Наявність цих переходів є фактом саме збереженої збірки; інший компілятор може обрати іншу реалізацію.

### `O3` з AVX2

```asm
vmovdqu ymm7, YMMWORD PTR [rdi+rax]
vpslld ymm0, ymm7, 1
vpaddd ymm0, ymm0, ymm7
vpaddd ymm0, ymm0, ymm5
vpsrld ymm0, ymm0, 1
vpaddd ymm0, ymm0, ymm4
vpmaxsd ymm1, ymm0, ymm6
vpcmpgtd ymm0, ymm0, ymm3
vpblendvb ymm0, ymm1, ymm2, ymm0
vmovdqu YMMWORD PTR [rcx+rax], ymm0
```

У цьому циклі сталі мають такі значення: `ymm5 = 1`, `ymm4 = -64`, `ymm6 = 0`, `ymm3 = 254`, `ymm2 = 255` у кожній 32-бітній позиції. Перші шість інструкцій формують вісім проміжних значень контрасту. `vpmaxsd` виконує знаковий максимум із нулем. `vpcmpgtd` формує маску для значень, більших за 254, а `vpblendvb` вибирає для них 255. Хоча остання інструкція вибирає байти, маска порівняння заповнює всі чотири байти відповідного 32-бітного елемента. Це реалізує потрібне насичення для всього елемента.

Важлива деталь: у фактичному основному циклі немає `vpminsd`. Верхню межу реалізовано порівнянням і вибором за маскою, а не векторним мінімумом. Також немає окремого умовного переходу для кожного пікселя всередині SIMD-блока.

## 3. Горизонтальний п’ятиточковий фільтр

Формула внутрішнього пікселя: `(left2 + 4*left1 + 6*center + 4*right1 + right2 + 8) >> 4`.

### `O0`

```asm
mov rax, QWORD PTR -40[rbp]
sal rax, 2
lea rdx, -8[rax]
mov rax, QWORD PTR -32[rbp]
add rax, rdx
mov ecx, DWORD PTR [rax]
; ...
shr edx, 4
mov DWORD PTR [rax], edx
add QWORD PTR -40[rbp], 1
```

Для кожного результату обчислюються адреси сусідніх пікселів, а індекс зберігається на стеку. Уже при `O0` деякі множення на малі сталі представлені додаваннями й зсувами. Отже, твердження «без оптимізації всі множення обов’язково залишаються `imul`» було б неправильним.

### `O3-scalar`

```asm
mov ecx, DWORD PTR -4[r9+rax*4]
add rax, 1
lea esi, [rdx+rdx*2]
mov edx, DWORD PTR [r9+rax*4]
mov r8d, DWORD PTR 4[r9+rax*4]
lea ebx, [rcx+rdx]
lea r8d, 8[r8+rbx*4]
add edi, r8d
lea esi, [rdi+rsi*2]
shr esi, 4
mov DWORD PTR -4[r10+rax*4], esi
```

Компілятор переорганізував суму й утримує частину сусідніх значень у регістрах для наступної ітерації. `lea` використовується як арифметика над регістрами: наприклад, множення на 3, а потім на 2 формує вагу 6. Запис залишається одним 32-бітним пікселем за ітерацію.

### `O3` з AVX2

```asm
vmovdqu ymm7, YMMWORD PTR [r8+rax]
vmovdqu ymm6, YMMWORD PTR [rcx+rax]
vpaddd ymm0, ymm6, YMMWORD PTR [r9+rax]
vmovdqu ymm5, YMMWORD PTR [rsi+rax]
vpslld ymm1, ymm7, 1
vpaddd ymm1, ymm1, ymm7
vpslld ymm1, ymm1, 1
vpaddd ymm1, ymm1, ymm2
vpaddd ymm0, ymm0, ymm1
vpaddd ymm1, ymm5, YMMWORD PTR [rdi+rax]
vpslld ymm1, ymm1, 2
vpaddd ymm0, ymm0, ymm1
vpsrld ymm0, ymm0, 4
vmovdqu YMMWORD PTR [rdx+rax], ymm0
add rax, 32
```

Це вісім сусідніх вихідних пікселів. Вхідні векторні завантаження перекриваються, бо кожен із восьми результатів потребує своїх п’яти сусідів. Зсуви формують ваги 4 та 6, а `ymm2` містить округлювальну сталу 8. Логічний зсув на 4 виконує ділення на 16. `vmovdqu` допускає невирівняні адреси, що зручно для зміщених сусідніх ділянок рядка.

## SIMD-ширина, краї та хвіст

256-бітний YMM-регістр містить `256 / 32 = 8` елементів `uint32_t`. У цих циклах `vpaddd`, `vpslld` і `vpsrld` виконують відповідну операцію над кожною позицією. Це означає обробку восьми елементів однією інструкцією певного виду; це не обіцянка восьмикратного прискорення всієї програми. Значення мають пропускна здатність пам’яті та кешів, кількість інструкцій, залежності, завантаження сусідів, частота CPU, службові частини програми й невекторизовані краї.

Коли довжина не кратна восьми, основний YMM-цикл не виходить за межі масиву. У збереженому коді після нього можливий 128-бітний XMM-блок на чотири елементи та скалярне завершення. Наприклад, у grayscale після векторного циклу є:

```asm
mov rax, r8
and rax, -8
test r8b, 7
je .L26
vzeroupper
```

`and ...,-8` визначає кількість уже оброблених елементів, кратну восьми. `test ... ,7` перевіряє залишок. Сама `vzeroupper` очищує верхні частини векторних регістрів; вона не виконує обробку хвоста. Далі код вибирає придатний шлях для залишку. Перші й останні два пікселі рядка blur додатково обробляються за правилом затискання індексів, незалежно від кратності довжини SIMD-ширині.

## Що підтверджено артефактами

Звіт GCC містить повідомлення `loop vectorized using 32 byte vectors` для основних циклів усіх трьох стадій, а також повідомлення про 16-байтні варіанти. У файлі `kernels_o3.s` є 48 рядків інструкцій із YMM-операндами; у `kernels_o0.s` та `kernels_scalar.s` таких рядків немає. Це статична характеристика тексту асемблера, а не кількість виконаних інструкцій чи апаратний лічильник.

Межі трьох стадій збережено через `noinline`, тому оптимізація помітно змінює їхні внутрішні цикли, але не усуває їхні імена. Вбудовування дрібних допоміжних функцій, усунення зайвих звернень до стеку та автоматична векторизація разом пояснюють зміни структури профілю. Конкретні частки часу потрібно брати з виміряного `perf report` і FlameGraph, а не виводити з розміру асемблерного файлу.

Семантику інструкцій AVX2 наведено в [Intel Software Developer’s Manual, Volume 2](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-2b-manual.pdf). Ключі, що дозволяють або вимикають автоматичну векторизацію, описано в [документації GCC](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html). Доказ використання інструкцій саме цією програмою — локальні `.s`-файли та дизасемблер, а не сама наявність AVX2 у характеристиках процесора.
