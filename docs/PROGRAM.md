# Досліджувана програма

Це оригінальна невелика програма на C++17 для обробки синтетичного зображення. Вона послідовно переводить RGB у відтінки сірого, підвищує контраст і виконує горизонтальне розмиття. Програма однопотокова. Файли зображень не читаються й не записуються: обчислення відокремлено від дискового вводу та виводу, щоб було зручніше дослідити роботу циклів, пам’яті та автоматичної векторизації.

Реалізація міститься у [main.cpp](../src/main.cpp), [kernels.cpp](../src/kernels.cpp) і [kernels.hpp](../src/kernels.hpp). Зовнішніх бібліотек для обробки зображень немає.

## Вхідні дані та пам’ять

Ширина `W`, висота `H`, кількість повторень і початкове значення генератора задаються аргументами. Наприклад:

```sh
./build/image_o3 --width 2048 --height 2048 --repeats 20 --seed 12345
```

`--size N` задає квадратне зображення `N × N`. Типові значення: `2048 × 2048`, 20 повторень, `seed = 12345`.

Генератор `xorshift32` послідовно формує значення каналів R, G, B у межах `0…255`. Його стан змінюється операціями `state ^= state << 13`, `state ^= state >> 17`, `state ^= state << 5`. Використовується молодший байт результату. Для `seed = 0` початковий стан явно замінюється на `0x9e3779b9`, щоб уникнути нульового нерухомого стану. Однакові аргументи дають однакові вхідні дані в усіх трьох збірках.

Кожен канал зберігається окремим масивом `uint32_t`, хоча значення поміщаються в один байт. Такий вибір спрощує цілочисельну арифметику та демонстрацію AVX2 над вісьмома 32-бітними елементами. Це навчальне подання даних, а не спроба мінімізувати розмір звичайного зображення.

Є шість масивів: R, G, B, grayscale, contrast та output. Обсяг саме їхніх елементів:

```text
6 × sizeof(uint32_t) × W × H = 24 × W × H байтів.
```

Для `2048 × 2048` це `100663296` байтів, тобто 96 MiB. Показник RSS додатково охоплює код, стек, бібліотеки, службові структури та інші сторінки процесу, тому не зобов’язаний дорівнювати цій формулі. Сума розмірів масивів також не є обсягом фактичного трафіку до RAM: частина читань обслуговується кешами, а деякі елементи використовуються повторно.

## Один прохід обробки

Позначимо індекс пікселя через `i = y × W + x`.

### 1. Переведення у відтінки сірого

Функція `rgb_to_grayscale` обчислює:

```text
gray[i] = floor((77 × R[i] + 150 × G[i] + 29 × B[i] + 128) / 256).
```

Ваги сумуються до 256. Додавання 128 перед зсувом забезпечує округлення до найближчого цілого з округленням половин угору. Це фіксована цілочисельна апроксимація зваженої яскравості, без перетворень колірного простору та гамма-корекції. Результат лежить у межах `0…255`.

### 2. Підвищення контрасту

Функція `adjust_contrast` обчислює:

```text
v = floor((3 × gray[i] + 1) / 2) - 64;
contrast[i] = min(255, max(0, v)).
```

Це коефіцієнт підсилення приблизно 1,5 навколо середини діапазону, з насиченням на 0 та 255. Віднімання виконується у знаковому типі `int32_t`, тому від’ємні проміжні значення обробляються коректно. Саме наведену формулу, включно з округленням, потрібно використовувати для перевірки результату.

### 3. Горизонтальне розмиття

Функція `horizontal_blur_5tap` використовує п’ять сусідніх значень того самого рядка з вагами `1, 4, 6, 4, 1`:

```text
output[y,x] = floor((C[y,x-2] + 4 × C[y,x-1] + 6 × C[y,x]
                     + 4 × C[y,x+1] + C[y,x+2] + 8) / 16).
```

Тут `C` — масив contrast. За межами рядка індекс затискається до найближчого краю: `x' = min(W-1, max(0, x))`. Розмиття лише горизонтальне, рядки не змішуються. Внутрішня частина рядка має прямий цикл, а перші й останні два пікселі обробляються окремо. Для ширин менше 5 усі пікселі проходять через обробку країв.

Сума перед діленням не перевищує `16 × 255 + 8 = 4088`, тому 32-бітного беззнакового типу достатньо. Усі три стадії зберігають діапазон `0…255`, а цілочисельний результат точно збігається між варіантами компіляції.

## Для чого потрібні повторення та обмін буферів

Після кожного проходу `red.swap(output)` міняє місцями два масиви. Отже, на наступній ітерації попередній результат розмиття стає новим R, а початкові G і B залишаються фіксованими. Це свідомо визначений ітеративний алгоритм: повторення обробки не є незалежними копіями одного й того самого зображення.

Обмін не копіює пікселі. Він змінює власників буферів, а шість виділених ділянок пам’яті залишаються різними. Залежність між ітераціями та використання кінцевого результату перешкоджають видаленню обчислень як непотрібної роботи. Функції стадій також містяться в окремому файлі компіляції, а LTO не використовується.

Після останнього проходу кінцевий результат перебуває в `red`. Для нього один раз поза вимірюваною ділянкою обчислюється 64-бітна контрольна сума:

```text
hash = 14695981039346656037;
для кожного uint32_t value:
    hash = (hash XOR value) × 1099511628211 modulo 2^64.
```

Це явно визначена контрольна сума для порівняння результатів, не криптографічний доказ правильності. У JSON вона записується десятковим рядком, щоб програми з числами IEEE 754 не втратили точність великого цілого.

## Що саме вимірюється

Поле `compute_seconds` — тривалість ділянки між двома викликами `std::chrono::steady_clock`: усі повторення трьох стадій і обміни буферів. Виділення й початкова ініціалізація пам’яті, кінцева контрольна сума та друк JSON відбуваються поза цією ділянкою. Сторінки масивів уже торкаються під час початкового заповнення.

Зовнішні `/usr/bin/time`, `perf stat` і `perf record`, запущені для всієї команди, охоплюють цілий процес: запуск, ініціалізацію, обчислення, контрольну суму, вивід і завершення. Тому їхні часові показники та профілі мають іншу область вимірювання. На FlameGraph у такому випадку можуть бути видимі генератор даних, виділення пам’яті й стандартна бібліотека.

Програма не виконує внутрішнє прогрівання та не закріплює потік за ядром. Зовнішній сценарій вимірювання має однаково задавати ці умови для всіх збірок. Порівнюються однакові `W`, `H`, `repeats` і `seed`; кількість повторень не можна збільшувати лише для швидшого варіанта в таблиці прямого порівняння.

## Три варіанти компіляції

| Файл Linux | Ключі, що розрізняються | Призначення |
|---|---|---|
| `image_o0` | `-O0` | Показати виконання без більшості оптимізацій компілятора |
| `image_scalar` | `-O3 -fno-tree-vectorize -fno-tree-slp-vectorize` | Порівняти оптимізовані скалярні цикли з SIMD |
| `image_o3` | `-O3` | Дозволити звичайні оптимізації та автоматичну векторизацію |

Фактично збережені Linux-збірки створено GCC 13 із спільним `-mavx2`. Також однаково задано `-g -fno-omit-frame-pointer` для символів і розкручування стеків. Ключ `-mavx2` дозволяє використання інструкцій AVX2; сам по собі він не доводить, що кожен цикл векторизовано. Доказ наведено в [розборі асемблера](ASSEMBLY.md).

`O0` — штучна навчальна базова версія. Велика різниця з нею не означає таке саме прискорення вже оптимізованої реальної програми. Зіставлення `O3-scalar` та `O3` краще показує наслідки дозволу векторизації, але й воно може включати пов’язані зміни розкладу інструкцій та структури циклу. Значення ключів оптимізації пояснює [документація GCC](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html).

Усі три стадії позначено `noinline`: їхні окремі імена видно в профілі та асемблері. Це свідоме обмеження для зрозумілого захисту; воно може обмежувати максимальну оптимізацію порівняно зі злиттям стадій. `restrict` використано лише для фактично різних буферів. LTO вимкнено/не вмикається. Немає ручних AVX-intrinsics, багатопотоковості чи зміни точності арифметики.

Для MSVC у CMake відповідником оптимізованих варіантів є `/O2`, а не буквальний ключ `-O3`; скалярна версія додатково використовує `/Qvec-`. Збережені результати асемблера стосуються Linux/GCC, не MSVC.

## Перевірка правильності

```sh
make ARCH_FLAGS=-mavx2 test
```

Параметр `--self-test` виконує 722 перевірки: вузькі зображення, краї рядків, довжини біля SIMD-меж, некратні довжини, чотири seed і кілька послідовних кроків. Незалежна еталонна реалізація обчислює кожен вихідний піксель без повторного використання функцій основних стадій. Додатково перевіряються повністю чорний і повністю білий входи з відомими результатами.

Усі три варіанти пройшли ці перевірки. Окрема збірка з AddressSanitizer та UndefinedBehaviorSanitizer також пройшла self-test. Ще чотири навантаження дали однакові контрольні суми між усіма збірками, а дев’ять помилкових варіантів аргументів правильно відхилено. Сирі результати збережено в [results/validation](../results/validation/). Самоперевірка та санітайзери не є вимірюванням продуктивності.
