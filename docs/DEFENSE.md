# Сценарій захисту на 8–12 хвилин

Це план власної демонстрації з екраном, камерою та голосом. Він не є записаним або завантаженим відео. Перед записом потрібно переглянути [PROGRAM.md](PROGRAM.md), [ASSEMBLY.md](ASSEMBLY.md) і підсумковий [REPORT.md](REPORT.md), відкрити сирі результати та підготувати місце для камери, яке не перекриває команди й графіки.

Числа під час пояснення слід читати з фактично створеного `results/analysis/summary.json` або звіту. Відомі підсумки Linux-серії наведено наприкінці цього сценарію; енергетичні значення потрібно брати з фінальної синхронізованої серії. Не називати невиміряні показники та не підміняти основні результати коротким демонстраційним запуском.

## 0:00–1:00. Задача, програма й правильність

Показати структуру репозиторію, три стадії в `src/kernels.cpp`, параметри запуску та таблицю варіантів у README.

Пояснення своїми словами:

> Я досліджую власну однопотокову C++17 програму, що переводить RGB у відтінки сірого, підвищує контраст і виконує горизонтальне розмиття з п’ятьма вагами. Досліджуються той самий вихідний код і однакові дані. Після кожної ітерації результат стає новим червоним каналом, тому всі повторення залежать від попередніх. Читання й запису файлів зображення в обчислювальному циклі немає.

Показати `build/image_o0`, `build/image_scalar`, `build/image_o3`. Пояснити `-O0`, `-O3` і вимкнення векторизації у скалярному контролі. Виконати:

```bash
make test ARCH_FLAGS=-mavx2
```

У кожної збірки має бути `status: pass` і 722 перевірки. Відкрити `results/linux-main/checksums.json`: основне навантаження має однакову контрольну суму в усіх версіях. Еталонні перевірки порівнюють пікселі, а контрольна сума додатково контролює однаковість великих запусків.

## Підготовка окремої папки живої демонстрації

Відкрити термінал Ubuntu 24.04. Якщо початок у PowerShell, спочатку виконати `wsl -d Ubuntu-24.04`, а далі команди нижче виконувати вже в Bash:

```bash
cd /mnt/q/Documents/CodexFiles/2026-10-23/x20/outputs/performance-lab
export LC_ALL=C
export PERF=/usr/lib/linux-tools/6.8.0-147-generic/perf
"$PERF" --version
bash scripts/linux/fetch_flamegraph.sh
DEMO=$(mktemp -d "results/demo-$(date -u +%Y%m%dT%H%M%SZ)-XXXXXX")

printf 'Fresh demonstration directory: %s\n' "$DEMO"
```

На поточному комп’ютері вказано фактично встановлений виконуваний файл `perf`, оскільки загальна оболонка `/usr/bin/perf` може шукати іншу версію для WSL-ядра. На іншому комп’ютері потрібно вибрати його реальний шлях. `mktemp` створює унікальну папку `results/demo-<UTC-час>-<суфікс>`: зібрані раніше дані не перезаписуються.

**У короткій демонстрації — 100 повторень. В основних збережених вимірюваннях — 300.** Порівнювати O0 з O3 у межах демонстрації можна, бо обидві команди нижче мають однакові аргументи. Значення з цих двох навантажень не можна змішувати в одній таблиці прискорення. Профіль O3 при коротшому запуску міститиме менше семплів; для точнішого аналізу використовується збережена основна серія.

## 1:00–2:30. GNU time та perf stat

Продемонструвати запуск обох версій із повним виводом GNU time:

```bash
for variant in image_o0 image_o3; do
  /usr/bin/time --verbose --output "$DEMO/$variant/time.txt" \
    taskset -c 0 "./build/$variant" \
    --width 2048 --height 2048 --repeats "$DEMO_REPEATS" --seed 12345 \
    > "$DEMO/$variant/time-program.json"
done
cat "$DEMO/image_o0/time.txt"
cat "$DEMO/image_o3/time.txt"
```

Показати й пояснити user time, system time, elapsed time, maximum RSS, minor/major page faults і context switches. `compute_seconds` усередині JSON охоплює лише повторення стадій та обміни буферів; GNU time охоплює весь процес. Завантаження CPU близько 100% для однопотокової програми означає приблизно один зайнятий логічний CPU, а не весь багатоядерний комп’ютер. Незначні page faults при виділенні пам’яті не означають обов’язкового читання з диска.

Далі запустити апаратні лічильники окремим проходом:

```bash
for variant in image_o0 image_o3; do
  "$PERF" stat -d --no-big-num --output "$DEMO/$variant/perf-stat.txt" -- \
    taskset -c 0 "./build/$variant" \
    --width 2048 --height 2048 --repeats "$DEMO_REPEATS" --seed 12345 \
    > "$DEMO/$variant/perf-program.json"
done
cat "$DEMO/image_o0/perf-stat.txt"
cat "$DEMO/image_o3/perf-stat.txt"
```

Пояснити `instructions`, `cycles`, `IPC = instructions/cycles`, branches, branch-misses, L1 loads і L1 misses. Вищий IPC сам по собі не доводить швидше виконання: потрібно враховувати кількість інструкцій, циклів і час. `<not supported>` для LLC на цьому WSL — відсутність вимірювання, а не нуль промахів. Прив’язка через `taskset -c 0` не забороняє іншим процесам користуватися фізичним ядром.

Для основних висновків показати збережені п’ять запусків на варіант у `results/linux-main/time/` та `perf-stat/`, медіану й спостережуваний min–max у звіті. Min–max — розкид цієї серії, не довірчий інтервал.

## 2:30–4:30. Побудова FlameGraph від запису до SVG

Цей етап потрібно показати під час захисту, а не лише відкрити готовий малюнок. Команди зберігають кожну проміжну форму. Однакова подія, частота й кількість повторень використовуються для O0 та O3:

```bash
for variant in image_o0 image_o3; do
  "$PERF" record -e cpu-clock:u -F 199 --call-graph dwarf,16384 \
    -o "$DEMO/$variant/perf.data" -- \
    taskset -c 0 "./build/$variant" \
    --width 2048 --height 2048 --repeats "$DEMO_REPEATS" --seed 12345 \
    > "$DEMO/$variant/record-program.json" \
    2> "$DEMO/$variant/record.stderr.txt"

  "$PERF" script -i "$DEMO/$variant/perf.data" \
    > "$DEMO/$variant/stacks.txt" 2> "$DEMO/$variant/script.stderr.txt"

  perl tools/FlameGraph/stackcollapse-perf.pl "$DEMO/$variant/stacks.txt" \
    > "$DEMO/$variant/stacks.folded"

  perl tools/FlameGraph/flamegraph.pl --hash --countname nanoseconds \
    --title "CPU FlameGraph: $variant, demonstration $DEMO_REPEATS repeats" \
    --subtitle "Period-weighted CPU time; widths normalized per graph; x-axis is not chronological" \
    "$DEMO/$variant/stacks.folded" > "$DEMO/$variant/flamegraph.svg"
done
```

Показати файли `perf.data`, початок текстових стеків і згорнутих стеків:

```bash
sed -n '1,18p' "$DEMO/image_o0/stacks.txt"
sed -n '1,5p' "$DEMO/image_o0/stacks.folded"
printf '%s\n' "$DEMO/image_o0/flamegraph.svg" "$DEMO/image_o3/flamegraph.svg"
```

Відкрити SVG-файли з надрукованих шляхів у браузері або VS Code. Вони зберігаються в репозиторії, видимому також у Windows. Збільшити одну широку ділянку натисканням, повернути масштаб і скористатися пошуком `adjust_contrast` або `horizontal_blur_5tap`.

Пояснення:

> `perf record` періодично бере семпли стеків. `perf script` перетворює їх у текст, `stackcollapse-perf.pl` групує однакові стеки та в цьому форматі сумує значення періодів, а `flamegraph.pl` створює інтерактивний SVG. Для `cpu-clock:u` ці ваги вимірюються в наносекундах. Ширина блоку показує частку сумарної ваги CPU-профілю з цією функцією у стеку; висота — глибину викликів. Вісь X не є перебігом часу. Кольори тут задаються хешем і не означають температуру або інтенсивність.

Великі цілі числа в `stacks.folded` — ваги періодів, а не кількість зібраних семплів. Точну кількість семплів показують `record.stderr.txt` і стовпці Samples у `perf report`; його заголовок може скорочувати тисячі до `3K`. Не називати суму folded-ваг мільярдами семплів.

Порівняти зі збереженими основними графіками в `results/linux-main/profiles/image_o0/` та `image_o3/`. Назвати широкі фактичні функції й їхні частки зі звіту. У O0 звернути увагу на `std::min/max` під контрастом, якщо вони присутні в профілі; в O3 їхня логіка вбудована. Ширина кожного SVG нормована на його власну суму ваг періодів: за двома однаково широкими полотнами не можна визначити абсолютне прискорення. Час порівнюється окремо.

## 4:30–5:30. perf report після perf record

```bash
for variant in image_o0 image_o3; do
  "$PERF" report --stdio --show-nr-samples --no-children \
    -i "$DEMO/$variant/perf.data" > "$DEMO/$variant/report-self.txt"
  "$PERF" report --stdio --show-nr-samples \
    -i "$DEMO/$variant/perf.data" > "$DEMO/$variant/report-inclusive.txt"
done
sed -n '1,55p' "$DEMO/image_o0/report-self.txt"
sed -n '1,55p' "$DEMO/image_o3/report-self.txt"
```

Пояснити різницю між власними семплами функції та її вкладеними викликами. У таблиці без children функція з великими дочірніми витратами може мати невелику власну частку; це не суперечить широкому батьківському блоку на FlameGraph. За потреби відкрити інтерактивний `"$PERF" report -i "$DEMO/image_o3/perf.data"` та завершити його клавішею `q`.

Подія `cpu-clock:u` описує користувацький CPU-час і не охоплює все очікування чи всі витрати ядра. Частота 199 Гц — цільова частота семплювання, а не гарантія точної кількості семплів. Профілювання має власні витрати, тому його тривалість не використовується як основний замір швидкості.

## 5:30–7:00. Оптимізація, асемблер та AVX2

Відкрити [ASSEMBLY.md](ASSEMBLY.md) поряд із `results/assembly/kernels_o0.s`, `kernels_scalar.s` і `kernels_o3.s`. Показати одну й ту саму функцію в усіх варіантах. Для свіжого дизасемблера можна виконати:

```bash
objdump -d -Mintel --disassemble=rgb_to_grayscale build/image_o0 \
  > "$DEMO/grayscale-o0.asm.txt"
objdump -d -Mintel --disassemble=rgb_to_grayscale build/image_scalar \
  > "$DEMO/grayscale-scalar.asm.txt"
objdump -d -Mintel --disassemble=rgb_to_grayscale build/image_o3 \
  > "$DEMO/grayscale-o3.asm.txt"
```

Пояснити такі факти з реального коду:

- У O0 багато завантажень зі стеку, а `std::min/max` залишаються викликами.
- У O3-scalar індекси й адреси утримуються в регістрах, дрібні функції вбудовані, але результат обробляється по одному пікселю.
- У O3 YMM-регістр має 256 біт, тобто вісім 32-бітних елементів. `vpmulld`, `vpaddd` і `vpsrld` виконують множення, додавання та логічні зсуви над ними.
- Для contrast фактичні інструкції — `vpmaxsd`, `vpcmpgtd`, `vpblendvb`; верхню межу тут реалізовано маскою, а не `vpminsd`.
- Краї blur та залишок некратної довжини обробляються коректно; після YMM-частини можливі XMM-блок і скалярний хвіст.

Показати рядки `loop vectorized using 32 byte vectors` у `results/assembly/vectorization_o3.txt`. Пояснити, що вісім позицій у регістрі не гарантують прискорення всієї програми у вісім разів. Ураховуються пам’ять, кеші, залежності, частота та службова робота. O0 є навчальною базовою версією; це не порівняння з уже оптимізованою виробничою програмою.

## 7:00–9:00. Енергія та межі вимірювань

Показати основну папку `results/energy-sync-host-20261023T195827031Z`, її `configuration.json`, один `run-...json`, `measurements.csv` і `summary.json`. Назвати кількість реально завершених раундів і конкретні домени. Навести для O0 та O3 фактичні медіани енергії package, DRAM і оцінки після віднімання фону; числа взяти зі звіту або сирої зведеної таблиці. Початкова папка `energy-host-...` охоплювала також тривалий запуск WSL і не є основою кінцевого порівняння.

Пояснення:

> Через WSL Linux powercap на цьому комп’ютері не надав потрібних лічильників. На Windows доступний Energy Meter Interface. Він повертає накопичені показники апаратних доменів; різниця між початком і кінцем дає енергію в джоулях, а ділення на тривалість — середню потужність у ватах. Основний протокол READY/GO/DONE/ACK/RESULT запускає енергетичне вікно після готовності WSL і завершує його до закриття оболонки. У вікні є весь Linux-процес, включно з виділенням пам’яті, ініціалізацією та контрольною сумою, а також невеликі витрати зв’язку й датчиків. Package і DRAM зберігаються окремо. PP0 і PP1 не додаються до package, бо це його піддомени.

За потреби показати коротку живу серію в **окремому PowerShell 7**, із кореня репозиторію Windows:

```powershell
$demoEnergyRoot = Join-Path (Get-Location) ('results/demo-energy-' + [DateTimeOffset]::UtcNow.ToString('yyyyMMddTHHmmssfffZ'))
./scripts/windows/run_sync_energy_series.ps1 `
  -LinuxProjectPath '/mnt/q/Documents/CodexFiles/2026-10-23/x20/outputs/performance-lab' `
  -Distro Ubuntu-24.04 -Width 2048 -Height 2048 -Repeats 100 `
  -Cpu 0 -Rounds 1 -SettleSeconds 2 -OutputRoot $demoEnergyRoot
```

Скрипт створює всередині нової папки окремий каталог серії, перевіряє однакові аргументи й контрольні суми та виконує також вимірювання спокою порівнянної тривалості. Під час енергетичного вимірювання не запускати паралельно інші лабораторні команди. Запис екрана й камера самі створюють фонове навантаження; основна серія без запису та ця жива демонстрація мають різні умови. Одна демонстраційна серія зі 100 повтореннями не замінює основні раунди з 300 повтореннями.

Формула оцінки:

```text
E_incremental ≈ E_active_domain − P_idle_domain × T_active_domain.
```

Її потрібно пояснити як оцінку додаткових витрат запуску за припущенням порівнянного фону. Інші процеси, WSL, запуск і завершення програми, частота CPU та нагрів впливають на результат. Від’ємну оцінку не слід приховувати або автоматично замінювати нулем: вона вказує на вплив фону чи похибки такої моделі.

**Обов’язково сказати вголос: споживання всього комп’ютера з розетки не виміряне.** CPU package та DRAM не охоплюють довільно всю систему, накопичувачі, GPU, плату й втрати блока живлення. Для повного системного вимірювання потрібен зовнішній ватметр; є інструмент `scripts/linux/import_wattmeter.py` для обробки справжніх даних, але його наявність не є виконаним вимірюванням.

**Також сказати: точна енергія лише окремого PID не виміряна; наведено оцінку внеску запуску через віднімання фону.** Це слід відкрито пояснити викладачу для пунктів 3.1 і 3.2. Не заявляти, що обидві вимоги повністю закриті прямими апаратними вимірюваннями. Якщо потрібні саме повна система й точне віднесення до процесу, ці обмеження залишаються частиною результату.

При поясненні змін після оптимізації відрізняти потужність від енергії: коротше виконання може зменшити джоулі навіть за вищої середньої кількості ватів. Конкретний напрям і величину різниці для цієї роботи потрібно показати за фактичними числами; не припускати автоматично, що O3 споживає менше ватів.

| Питання | Суть відповіді |
|---|---|
| Чому саме C++ і така програма? | Є вихідний код, відтворювані дані та зрозумілі цикли для аналізу оптимізації й SIMD. |
| Чи прибрав оптимізатор обчислення? | Результат переходить у наступну ітерацію й використовується в кінцевій контрольній сумі; межі функцій збережені, LTO немає. |
| Чому `compiled_isa` однакове в усіх версіях? | Воно показує дозволений набір інструкцій. Реальну векторизацію підтверджує асемблер; у скалярному контролі її вимкнено. |
| Чи є FlameGraph часовою шкалою? | Ні. Тут ширина — частка сумарної ваги періодів CPU-clock, висота — вкладеність, порядок по X не є часом. |
| Чому O3 може мати інший IPC? | Змінився склад інструкцій і доступи до пам’яті. Сам IPC не замінює загальні цикли й час. |
| Чому час JSON відрізняється від GNU elapsed? | Області різні: цикл проти всього процесу. Але в цій WSL-серії іноді elapsed навіть менший за compute: це зафіксована неузгодженість часових джерел із невстановленою причиною. Віднімати їх як точну вартість підготовки не можна. |
| Чому не додаємо PP0, PP1 і PKG? | Це перекривні області; таке додавання двічі врахувало б частину енергії. |
| Чи виміряно весь ПК та тільки PID? | Весь ПК не виміряно. Для запуску є доменна оцінка після віднімання фону, не точний PID-лічильник. |
| Чи min–max є похибкою вимірювача? | Ні. Це фактично спостережуваний розкид кількох запусків, без заяви про довірчий інтервал чи точність сенсора. |
